Scheduling System Tasks

System jobs run as root for the whole server: system cron files, anacron, systemd timers, and temp-file cleanup. Plus a checklist when a job does not run.

Big picture/etc/cron.dcron.dailyanacronsystemd timerstmpfilesTroubleshootingCommands listQuiz

1User jobs vs system jobs

Why? User cron jobs belong to one user. System jobs (log cleanup, backups, updates) belong to the server, so they live in system files that admins and packages manage.

User jobs (chapter 3)

  • crontab -e
  • stored in /var/spool/cron/USER
  • 5 time fields + command
  • runs as that user

System jobs (this chapter)

  • files in /etc/cron.d/
  • scripts in /etc/cron.daily/ etc.
  • 6th field = user name
  • also systemd timers

2System cron: /etc/crontab and /etc/cron.d

Why? Packages and admins need to add system jobs without touching a user crontab. The system format has one extra field: who runs the job.
/etc/crontab (reference only, comments + empty by default)
SHELL=/bin/bash
PATH=/sbin:/bin:/usr/sbin:/usr/bin
MAILTO=root
# .---- minute (0 - 59)
# | .-- hour (0 - 23)
# | | .- day of month (1 - 31)
# | | | .- month (1 - 12)
# | | | | .- day of week (0 - 6)
# | | | | |
# * * * * * user-name  command to be executed
Do not edit /etc/crontabA package update can overwrite it. Create your own file inside /etc/cron.d/ instead.

Create a system job: exact file and line

  1. Create the file /etc/cron.d/diskreport (any name, no dot in name).
  2. Add the line below. Note the root user field.
  3. Save. No reload needed, crond reads the folder by itself.
/etc/cron.d/diskreport
MAILTO=root
0 4 * * 1  root  /usr/bin/df -h >> /var/log/diskreport.log 2>&1
$ ls -l /etc/cron.d/
-rw-r--r--. 1 root root 128 Nov 20 09:10 0hourly
-rw-r--r--. 1 root root 101 Nov 20 09:12 diskreport
RuleFiles in /etc/cron.d must be owned by root, not writable by others, and the file name must not contain a dot (a name like job.bak is ignored).

3cron.hourly, cron.daily, weekly, monthly

Why? For simple jobs you do not need time fields. Put an executable script in a folder and the system runs it at that interval.
FolderRuns
/etc/cron.hourly/every hour (at minute 1 past, via /etc/cron.d/0hourly)
/etc/cron.daily/once a day
/etc/cron.weekly/once a week
/etc/cron.monthly/once a month
$ sudo vim /etc/cron.daily/cleanup
$ sudo cat /etc/cron.daily/cleanup
#!/bin/bash
find /var/tmp/reports -type f -mtime +7 -delete
$ sudo chmod 755 /etc/cron.daily/cleanup
Scripts, not crontab linesThese folders hold executable shell scripts only. Without chmod +x (or a bad shebang) the script is skipped. A file name with a dot is skipped too.

How the daily run really works

/etc/cron.d/0hourly runs run-parts /etc/cron.hourly every hour. One of those hourly scripts starts anacron, and anacron decides when the daily, weekly and monthly folders run.

4anacron and /etc/anacrontab

Why? A laptop or VM may be switched off at 3 AM. Normal cron would skip the job. anacron (anachronistic cron) runs missed jobs when the system is back.
/etc/anacrontab
SHELL=/bin/sh
PATH=/sbin:/bin:/usr/sbin:/usr/bin
MAILTO=root
RANDOM_DELAY=45
START_HOURS_RANGE=3-22
#period  delay  job-identifier  command
1        5      cron.daily      nice run-parts /etc/cron.daily
7        25     cron.weekly     nice run-parts /etc/cron.weekly
@monthly 45     cron.monthly    nice run-parts /etc/cron.monthly
FieldMeaning
periodin days: 1 = daily, 7 = weekly, @monthly
delayminutes to wait after anacron starts
job-identifierunique name, also the timestamp file name
commandwhat to run
  • Timestamps are kept in /var/spool/anacron/. Anacron compares today with the stored date.
  • RANDOM_DELAY=45 adds up to 45 minutes of random delay, so many servers do not start together.
  • START_HOURS_RANGE=3-22 means jobs start only between 03:00 and 22:00.
$ sudo ls /var/spool/anacron
cron.daily  cron.monthly  cron.weekly
$ sudo cat /var/spool/anacron/cron.daily
20261120

5systemd timers

Why? systemd can also schedule jobs. A timer unit starts a matching service unit. Benefits: logs in the journal, dependencies, and easy status checks.

See existing timers

$ systemctl list-timers
NEXT                        LEFT     LAST                        PASSED  UNIT                         ACTIVATES
Sat 2026-11-21 00:00:00 IST 2h 14min Fri 2026-11-20 00:00:01 IST 21h ago logrotate.timer              logrotate.service
Sat 2026-11-21 09:35:12 IST 11h left Fri 2026-11-20 09:35:12 IST 12h ago systemd-tmpfiles-clean.timer systemd-tmpfiles-clean.service

Create your own timer: 3 steps

Scenario: run a disk report every day at 05:00.

1) /etc/systemd/system/diskreport.service
[Unit]
Description=Disk report

[Service]
Type=oneshot
ExecStart=/usr/bin/bash -c "df -h >> /var/log/diskreport.log"
2) /etc/systemd/system/diskreport.timer
[Unit]
Description=Run disk report daily

[Timer]
OnCalendar=*-*-* 05:00:00
Persistent=true

[Install]
WantedBy=timers.target
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now diskreport.timer
Created symlink '/etc/systemd/system/timers.target.wants/diskreport.timer' -> '/etc/systemd/system/diskreport.timer'.
$ systemctl list-timers diskreport.timer
NEXT                        LEFT    LAST PASSED UNIT             ACTIVATES
Sat 2026-11-21 05:00:00 IST 7h left -    -      diskreport.timer diskreport.service
Enable the .timer, not the .serviceYou start and enable diskreport.timer. The service is started by the timer.
Timer lineMeaning
OnCalendar=dailyevery day at 00:00
OnCalendar=Mon *-*-* 08:30:00every Monday 08:30
OnBootSec=15min15 minutes after boot
OnUnitActiveSec=1h1 hour after the service last ran
Persistent=truerun at next start if a run was missed (like anacron)
Test a calendar timesystemd-analyze calendar "Mon *-*-* 08:30" prints the next run time. Use it before you enable the timer.
$ systemd-analyze calendar "Mon *-*-* 08:30"
  Original form: Mon *-*-* 08:30
Normalized form: Mon *-*-* 08:30:00
    Next elapse: Mon 2026-11-23 08:30:00 IST

Check the result

$ systemctl status diskreport.service
$ journalctl -u diskreport.service --since today

6systemd-tmpfiles: temporary files

Why? /tmp and /var/tmp fill up with old files. systemd-tmpfiles (temporary files) creates and cleans them by rules, run by a timer.
Config folderWho writes it
/usr/lib/tmpfiles.d/packages (do not edit)
/etc/tmpfiles.d/admin rules, win over packages
/run/tmpfiles.d/volatile rules
/etc/tmpfiles.d/reports.conf
# Type Path               Mode UID  GID  Age
d      /run/reports       0750 root root 30d
  • d = create the directory if it does not exist, and clean files older than Age.
  • Mode 0750, owner root, group root. Age 30d = 30 days.
$ sudo systemd-tmpfiles --create /etc/tmpfiles.d/reports.conf
$ ls -ld /run/reports
drwxr-x---. 2 root root 40 Nov 20 10:05 /run/reports
$ sudo systemd-tmpfiles --clean
Who runs the clean?systemd-tmpfiles-clean.timer runs systemd-tmpfiles --clean about 15 minutes after boot and then every day. Default age for /tmp is 10 days, for /var/tmp 30 days.

7Cron troubleshooting

Why? A scheduled job that silently fails is dangerous. This checklist finds the problem in order.
  1. Is the service running? systemctl status crond (or atd).
  2. Is the line there and correct? crontab -l or cat /etc/cron.d/NAME.
  3. Did cron try to run it? grep CRON /var/log/cron or journalctl -u crond.
  4. Is the script executable with full paths? ls -l script.sh.
  5. Run the exact command by hand as the same user.
  6. Read the output file or mail (2>&1 in the line).
$ sudo systemctl status crond | head -4
● crond.service - Command Scheduler
     Loaded: loaded (/usr/lib/systemd/system/crond.service; enabled)
     Active: active (running) since Fri 2026-11-20 08:01:12 IST
$ sudo tail -2 /var/log/cron
Nov 20 10:00:01 server CROND[3105]: (root) CMD (/usr/bin/df -h >> /var/log/diskreport.log 2>&1)
SymptomLikely cause
Job never startscrond stopped, or file name with a dot in /etc/cron.d
Runs but command not foundshort PATH, use the full path
Works by hand, fails in cronno environment, aliases and variables missing
Script in cron.daily skippedno execute bit or bad file name
Wrong timewrong field order, or server time zone differs (timedatectl)
