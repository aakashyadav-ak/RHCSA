Scheduling User Tasks

Run a command later with at, or again and again with cron. You will learn the exact commands, the time fields, and how to see the output of a job.

1Why scheduling? Two kinds of jobs

Why? Admins cannot sit at the server all night. Scheduling lets Linux run backups, cleanups and reports by itself, at the right time.

Service (daemon)atdcrond

Full formscron comes from Greek *chronos* = time. crontab = cron table (the list of jobs). atq = at queue. atrm = at remove. crond = cron daemon (a daemon is a background service).

2at: run a job one time

Why? You want a command to run once at a future time, for example a heavy report at midnight. at reads commands from you and runs them later.

First make sure the atd service is running. On a fresh RHEL 10 server you may have to install it.

$ sudo dnf install -y at
$ sudo systemctl enable --now atd
$ systemctl is-active atd
active

Schedule a job (type commands, finish with Ctrl+D)

$ at now +5 minutes
warning: commands will be executed using /bin/sh
at> date >> /tmp/at-test.txt
at> echo "backup done" >> /tmp/at-test.txt
at> <EOT>
job 3 at Fri Nov 20 22:35:00 2026

<EOT> appears when you press Ctrl+D. The number (3) is the job id. Remember it, you need it to remove the job.

Time formatMeaning
at now +10 minutes10 minutes from now
at 22:30today 10:30 PM (tomorrow if time has passed)
at 22:30 tomorrowtomorrow 10:30 PM
at 02:00 Dec 25a given date
at teatime4 PM (also noon, midnight)
at -f /root/job.sh 23:00run commands from a file

See and remove jobs

$ atq
3       Fri Nov 20 22:35:00 2026 a student
4       Sat Nov 21 02:00:00 2026 a student
$ at -c 3
#!/bin/sh
# atrun uid=1000 gid=1000
cd /home/student || exit 1
date >> /tmp/at-test.txt
echo "backup done" >> /tmp/at-test.txt
$ atrm 4
$ atq
3       Fri Nov 20 22:35:00 2026 a student
  • atq columns: job id, date and time, queue letter (a), owner.
  • at -c ID prints the full job, including saved environment. Use it to check what will run.
  • atrm ID deletes a job. A normal user sees only own jobs. root sees all.

Real scenario: safety job while changing the firewall

You change firewall rules on a remote server. If you lock yourself out, the old config must come back. Schedule a rollback first, and cancel it only if everything works.

$ sudo at now +10 minutes
at> firewall-cmd --reload
at> <EOT>
job 5 at Fri Nov 20 22:45:00 2026
# ...test the new rules. If all is fine, cancel the rollback:
$ sudo atrm 5
Output of at jobsat has no screen to print on. Output of the commands is sent as mail to the user. If you want to keep it, redirect it yourself: command >> /tmp/file.log 2>&1.

3Who may use at and cron

Why? The admin must be able to stop ordinary users from scheduling jobs on a shared server.
FileRule
/etc/at.allowonly users listed here may use at
/etc/at.denyeveryone may use at except the listed users
/etc/cron.allowonly users listed here may use crontab
/etc/cron.denyeveryone may use crontab except the listed users
Order of checkingThe allow file is read first. If it exists, deny is ignored. root is always allowed.
$ echo "student" | sudo tee -a /etc/cron.allow
student
$ crontab -e      # as user john, who is NOT in cron.allow
You (john) are not allowed to use this program (crontab)
See crontab(1) for more information

4cron: crontab -e, -l, -r

Why? Some tasks repeat: nightly backup, hourly cleanup. You write the job once in a crontab (cron table) and crond runs it forever.
$ sudo dnf install -y cronie
$ sudo systemctl enable --now crond
$ systemctl is-active crond
active
CommandWhat it does
crontab -eedit YOUR crontab in the default editor (vim). Saved on quit.
crontab -llist your jobs
crontab -rremove ALL your jobs. No question asked!
crontab -riremove all, but ask first (safer)
crontab -u john -eroot only: edit the crontab of user john
crontab file.txtreplace your crontab with a prepared file
-r is dangerouscrontab -r and crontab -e are next to each other on the keyboard. One wrong letter deletes every job without a warning. Keep a copy: crontab -l > ~/crontab.bak.

Add a job step by step

  1. Run crontab -e.
  2. Press i, then type the job line (below).
  3. Press Esc, type :wq and Enter.
  4. Check with crontab -l.
Line to add in crontab -e (file lives in /var/spool/cron/student)
# minute hour day-of-month month day-of-week  command
30 2 * * * /home/student/backup.sh >> /home/student/backup.log 2>&1
$ crontab -e
crontab: installing new crontab
$ crontab -l
# minute hour day-of-month month day-of-week  command
30 2 * * * /home/student/backup.sh >> /home/student/backup.log 2>&1
$ sudo ls /var/spool/cron/
student
Where is it stored?Every user crontab is a file named after the user in /var/spool/cron/. Never edit it by hand. Always use crontab -e, it checks the syntax.

5Cron time fields

Why? The 5 fields tell cron exactly when to run. If you read them in the wrong order, the job runs at the wrong time.
SymbolMeaningExample
*every value* * * * * = every minute
,list0 8,20 * * * = 8 AM and 8 PM
-range0 9 * * 1-5 = 9 AM, Monday to Friday
/step*/15 * * * * = every 15 minutes
LineRuns
30 2 * * *every day at 02:30
0 */2 * * *every 2 hours, at minute 0
15 18 * * 5every Friday at 18:15
0 0 1 * *1st of every month at midnight
0 6 1 1 *every 1 January at 06:00
@rebootonce, when the system starts
@dailysame as 0 0 * * * (also @hourly, @weekly, @monthly)
Common mistakes1) * 5 * * * runs every minute of hour 5 (60 times). Use 0 5 * * *. 2) A % in a command means new line in cron. Write \%. 3) If both day-of-month and day-of-week are set, the job runs when either matches.

Environment inside cron

Cron runs with a very small environment: short PATH, no aliases, home directory as start folder. So always use the full path of commands and scripts.

crontab -e (variables at the top apply to all jobs below)
SHELL=/bin/bash
PATH=/usr/local/bin:/usr/bin:/bin
0 3 * * * /usr/bin/dnf -q check-update > /tmp/updates.txt

6Cron output and MAILTO

Why? A cron job has no terminal. If it prints something or fails, the output has to go somewhere. By default cron mails it to the job owner.
crontab -e
MAILTO=student
0 1 * * * /home/student/report.sh
  • Anything the job prints (output or error) is mailed to the owner, or to the user in MAILTO.
  • MAILTO="" (empty) = send no mail at all.
  • Mail needs a mail system. On a minimal server nobody reads it, so most admins write to a log file.
$ mail
Heap mailbox '/var/spool/mail/student': 1 message
>N  1 root@server  Fri Nov 20 01:00  25/812  "Cron <student@server> /home/student/report.sh"

Best practice: write to a log file

crontab -e
0 1 * * * /home/student/report.sh >> /home/student/report.log 2>&1
0 2 * * * /home/student/clean.sh > /dev/null 2>&1
PartMeaning
>>append output to file (> would overwrite)
2>&1send errors (2) to the same place as output (1)
> /dev/null 2>&1throw everything away (silent job)

Did my job run? Check the log

$ sudo journalctl -u crond --since today
Nov 20 02:30:01 server CROND[2210]: (student) CMD (/home/student/backup.sh >> /home/student/backup.log 2>&1)
$ sudo grep CROND /var/log/cron | tail -3
Troubleshooting checklistJob not running? 1) systemctl status crond 2) crontab -l shows the line 3) script has chmod +x and full path 4) look in /var/log/cron 5) test the exact command by hand.
