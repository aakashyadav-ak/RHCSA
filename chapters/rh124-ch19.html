🔑 Configuring and Securing SSH

SSH lets you control a Linux server from anywhere, safely. It is the most used admin tool and the most attacked service on the Internet, so you must know both how to use it and how to lock it down.

🔏 Host Keys, Fingerprints and known_hosts

SSH has two different kinds of keys. Beginners often mix them up:

🖥️ Host key = the SERVER's identity
Proves to you "I really am server1". Lives on the server. Created automatically when sshd is first installed.
👤 User key = YOUR identity
Proves to the server "I really am student". The key pair you make with ssh-keygen (next section).
1. You connect
ssh server1
→
2. Server shows its host public key
→
3. Client checks known_hosts
seen before?
→
4a. Same key: connect
4b. Different: WARNING
WhereFileWhat it is
Server/etc/ssh/ssh_host_ed25519_keyHost private key. Secret, root only
Server/etc/ssh/ssh_host_ed25519_key.pubHost public key. This is what clients see. Also _rsa_ and _ecdsa_ versions
Client~/.ssh/known_hostsServers you trust
Client/etc/ssh/ssh_known_hostsServers trusted by all users of this machine

A fingerprint is a short "photo" (hash) of a long key, so humans can compare it. Same key = same fingerprint.

Step by step: connect safely the first time

Step 1: On the SERVER, find its real fingerprint (use the console or a trusted admin)

server1$ ls /etc/ssh/*.pub
/etc/ssh/ssh_host_ecdsa_key.pub  /etc/ssh/ssh_host_ed25519_key.pub  /etc/ssh/ssh_host_rsa_key.pub
server1$ ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub
256 SHA256:h/hEJa/anxp6AP7BmB5azIPVbPNqieh0oKi4KWOTK80 root@server1 (ED25519)

Step 2: On the CLIENT, connect and COMPARE

client$ ssh student@server1
The authenticity of host 'server1 (192.168.1.10)' can't be established.
ED25519 key fingerprint is SHA256:h/hEJa/anxp6AP7BmB5azIPVbPNqieh0oKi4KWOTK80.   # same as Step 1? good
Are you sure you want to continue connecting (yes/no/[fingerprint])? yes
Warning: Permanently added 'server1' (ED25519) to the list of known hosts.
If the strings match, type yes. If not, type no and report it. Never type yes without checking on a real network.

Step 3: Look at what was saved

client$ cat ~/.ssh/known_hosts
server1,192.168.1.10 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIJ3x...
# field 1: hostname,IP    field 2: key type    field 3: the public key
client$ ssh-keygen -F server1          # find one host's entry
# Host server1 found: line 1
client$ ssh-keygen -lf ~/.ssh/known_hosts      # show fingerprints of all saved hosts
client$ ls -l ~/.ssh/known_hosts
-rw-------. 1 student student 202 Nov  1 11:30 /home/student/.ssh/known_hosts
Some systems store hostnames as scrambled hashes (|1|abc...) so a thief cannot read your server list. That is normal. Use ssh-keygen -F name to search.

→

🏢 Scenario: a cloned VM has the same host key as the original

Two servers sharing one host key is a security problem. On the clone, make new keys:
clone$ sudo rm /etc/ssh/ssh_host_*
clone$ sudo ssh-keygen -A               # creates all missing host keys
clone$ sudo systemctl restart sshd
# every client will now see the CHANGED warning once. Run ssh-keygen -R clone-name

3. Key-Based Login (no password)

A key pair has two files. The private key stays secret on your machine. The public key is copied to the server. Like a lock (public) and its only key (private).

1. ssh-keygen
makes the pair
→
2. ssh-copy-id
puts the public key in the server's authorized_keys
→
3. ssh user@ip
client proves it owns the private key
→
✔ logged in, no password sent
$ ssh-keygen                           # Enter 3 times, or set a passphrase (recommended)
Your identification has been saved in /home/student/.ssh/id_rsa
Your public key has been saved in /home/student/.ssh/id_rsa.pub
$ ssh-keygen -t ed25519 -C "student@laptop"     # modern, short, fast (preferred)
$ ssh-keygen -t rsa -b 4096                     # RSA, -t = type, -b = bits
$ ssh-copy-id -i ~/.ssh/id_rsa.pub student@192.168.1.10
Number of key(s) added: 1
$ ssh student@192.168.1.10             # no password asked now
$ ls -l ~/.ssh/                        # on the server: check authorized_keys exists
-rw-------. 1 student student  563 Nov  1 11:10 authorized_keys
Key fileModeShare it?
~/.ssh/id_rsa (private)600NEVER
~/.ssh/id_rsa.pub (public)644Yes
~/.ssh/ folder700-
authorized_keys600-
Careful: running ssh-keygen with an existing file name overwrites your old key pair. Servers that had the old public key will reject you until you copy the new one. Use -f ~/.ssh/other_name for a second key.
Two ways to share a key: (1) create the key on the client and copy the public part to the server (usual way), or (2) create it on the server and give the private key safely to the user. Way 1 is safer because the private key never travels.

Extras you should know

$ eval $(ssh-agent) ; ssh-add          # type the passphrase once per session
$ ssh -v student@server1               # debug: see which key and method is used

📍 Where to Add What: save typing with ~/.ssh/config (client)

Host web1
    HostName 192.168.1.10
    User student
    Port 22
    IdentityFile ~/.ssh/id_ed25519
Now ssh web1 does everything. Run chmod 600 ~/.ssh/config. To reach an internal server through a jump host, add ProxyJump external, or run ssh -J external internal.

🔐 Passphrase Protection and ssh-agent

A key without a passphrase is like a house key with your address on it: whoever finds it can walk in. A passphrase locks the private key file itself. A thief needs the file and the passphrase. The passphrase never travels to the server. It only unlocks the key on your computer.

PasswordPassphrase
ProtectsThe account on the serverThe private key file on your machine
Sent over the network?Yes (encrypted)Never

Step by step

Step 1: Create a key WITH a passphrase

$ ssh-keygen -t ed25519 -f ~/.ssh/id_work
Enter passphrase (empty for no passphrase): ********     # type it. You will not see it
Enter same passphrase again: ********
Your identification has been saved in /home/student/.ssh/id_work
Your public key has been saved in /home/student/.ssh/id_work.pub
-f chooses the file name, so your other keys stay safe. Already have a key with no passphrase? Add one: ssh-keygen -p -f ~/.ssh/id_rsa.

Step 2: Install the public key on the server

$ ssh-copy-id -i ~/.ssh/id_work.pub student@server1
student@server1's password:          # the ACCOUNT password, needed this one time
Number of key(s) added: 1

Step 3: Log in. Now it asks for the PASSPHRASE

$ ssh -i ~/.ssh/id_work student@server1
Enter passphrase for key '/home/student/.ssh/id_work':     # passphrase, not account password
[student@server1 ~]$
It is safe, but typing it every time is boring. That is the job of the agent.

ssh-agent: type the passphrase once

Start the agent
eval $(ssh-agent)
→
Load the key once
ssh-add ~/.ssh/id_work
→
Agent keeps it unlocked in memory
→
Every ssh uses it, no prompt

Step 4: Start the agent

$ eval $(ssh-agent)
Agent pid 10155
ssh-agent prints commands that set two variables (SSH_AUTH_SOCK, SSH_AGENT_PID). eval runs them in your current shell. Without eval nothing is set.

Step 5: Add the key, check, and log in

$ ssh-add ~/.ssh/id_work
Enter passphrase for /home/student/.ssh/id_work:      # last time you type it
Identity added: /home/student/.ssh/id_work (student@laptop)
$ ssh-add -l                                           # list loaded keys
256 SHA256:Qk1... student@laptop (ED25519)
$ ssh -i ~/.ssh/id_work student@server1                # no passphrase prompt now

Step 6: Remove keys when done

$ ssh-add -D            # remove all keys from the agent
$ ssh-agent -k          # stop the agent
The agent works only in the shell that started it (and programs started from it). Open a second terminal and it asks for the passphrase again, because that shell has no agent variables. Logging out clears the keys from memory. On a GNOME desktop, the agent starts for you automatically.

📍 Where to Add What: load the key automatically on first use

Add to ~/.ssh/config on the client: 
Host *
    AddKeysToAgent yes
    IdentityFile ~/.ssh/id_work
The first ssh asks for the passphrase and adds the key to a running agent. You still need the agent started once per session.

4. Configuring the Server: sshd_config

📍 Where to Add What

Edit /etc/ssh/sshd_config as root and add or change these lines: 
PermitRootLogin yes          # allow root login (default varies. Check with: sshd -T | grep permitroot)
AllowUsers xyz abc           # ONLY these users may log in
DenyUsers  baduser           # these users are always blocked
Then apply it: sudo systemctl reload sshd (or restart).
Spelling matters: PermitRootLogin (not Loging) and reload (not relod). A wrong word makes sshd refuse to load. Always run sudo sshd -t first. No output means OK.
SettingMeaning
PermitRootLogin yes|no|prohibit-passwordCan root log in? prohibit-password = only with a key
PasswordAuthentication yes|noAllow passwords?
PubkeyAuthentication yesAllow keys (never turn off)
AllowUsers / AllowGroupsWhitelist. Everyone else is denied
DenyUsers / DenyGroupsBlacklist
Port 2222Change the port
Order of checks: DenyUsers → AllowUsers → DenyGroups → AllowGroups. A user on the deny list is blocked even if also allowed. Drop-in warning: in OpenSSH the first value read wins, and the main file starts with Include /etc/ssh/sshd_config.d/*.conf. A setting in a drop-in file can beat your edit in the main file. Always check the real value with sudo sshd -T | grep -Ei 'permitrootlogin|passwordauth|allowusers'.

🏢 Scenario: only two admins may use SSH

$ sudo vim /etc/ssh/sshd_config.d/40-access.conf       # add: AllowUsers xyz abc
$ sudo sshd -t && sudo systemctl reload sshd
$ ssh mallory@server1
mallory@server1: Permission denied (publickey,gssapi-keyex,gssapi-with-mic,password).
$ sudo journalctl -u sshd -n 2
sshd[3011]: User mallory from 192.168.1.50 not allowed because not listed in AllowUsers

6. Transferring Files over SSH

$ scp file.txt student@192.168.1.10:/home/student/      # upload
$ scp student@192.168.1.10:/home/student/file.txt .     # download to current folder (the dot)
$ scp -r project/ student@server1:/srv/                  # whole folder (-r)
$ scp -P 2222 file.txt student@server1:/tmp/             # capital P for port in scp
$ sftp student@server1                                   # interactive: get, put, ls, exit
$ rsync -av -e ssh /data/ student@server1:/backup/       # only copies changes

7. Firewall: Allow or Block by IP and Port

The firewall decides who can even reach port 22. On RHEL use firewalld (firewall-cmd). The older tool iptables does the same job: accept or drop traffic from an IP or port.

Goalfirewalld (RHEL way)iptables (older)
Allow SSHfirewall-cmd --permanent --add-service=sshiptables -A INPUT -p tcp --dport 22 -j ACCEPT
Allow only one IPfirewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="192.168.1.50" service name="ssh" accept'iptables -A INPUT -p tcp -s 192.168.1.50 --dport 22 -j ACCEPT
Block an IPfirewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="10.0.0.9" drop'iptables -A INPUT -s 10.0.0.9 -j DROP
Apply / savefirewall-cmd --reload (permanent is saved)Rules are lost at reboot unless saved
Order matters in iptables: a DROP placed before an ACCEPT wins. Do not run iptables and firewalld together. Pick one (firewalld on RHEL). Never block port 22 on a remote server unless you have another way in.

🔒 SSH Hardening Project

Goal: take a default SSH server and make it hard to attack, without locking yourself out. Think in layers: if one fails, the next still protects you.

Layer 1: Network. Firewall allows port 22 only from trusted IPs. Optional fail2ban bans guessers.
Layer 2: Service. sshd settings: no root, limited tries, short login window, no empty passwords.
Layer 3: Authentication. Keys only (with passphrase). Passwords off.
Layer 4: Authorisation. AllowUsers or AllowGroups. Admins use sudo, not root.
Layer 5: Watching. Logs, lastb, alerts, and regular review.

Step-by-step

Step 0: Safety first

$ sudo cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak.$(date +%F)    # backup
$ ssh student@server1        # KEEP this session open until the very end. It is your lifeline.

Step 1: Create a normal admin user with sudo

$ sudo useradd -m -G wheel admin1 ; sudo passwd admin1      # wheel group = sudo rights on RHEL

Step 2: Set up keys for that user, then test in a second terminal

client$ ssh-keygen -t ed25519
client$ ssh-copy-id admin1@server1
client$ ssh admin1@server1 && sudo whoami           # must print: root
Do not continue until this works.

📍 Step 3: Where to Add What

Create the file /etc/ssh/sshd_config.d/40-hardening.conf (name starts with 40 so it is read before RHEL's own 50-redhat.conf, and the first value wins): 
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
PermitEmptyPasswords no
AllowUsers admin1 student
MaxAuthTries 3
LoginGraceTime 30
ClientAliveInterval 300
ClientAliveCountMax 2
X11Forwarding no
Banner /etc/issue.net
LineWhy
PermitRootLogin noEveryone knows the username "root", so attackers only need a password. Also loses audit trail
PasswordAuthentication noStops password guessing completely
PermitEmptyPasswords noBlocks accounts with no password
AllowUsersWhitelist: only named accounts can even try
MaxAuthTries 3Disconnects after 3 wrong attempts
LoginGraceTime 3030 seconds to log in, then the connection is dropped
ClientAliveInterval 300 + CountMax 2Drops idle sessions after about 10 minutes
X11Forwarding noRemoves an unneeded feature (less attack surface)

Step 4: Test, check the real values, apply

$ sudo sshd -t                         # no output = syntax OK
$ sudo sshd -T | grep -Ei 'permitrootlogin|passwordauthentication|allowusers|maxauthtries'
permitrootlogin no
passwordauthentication no
maxauthtries 3
allowusers admin1 student
$ sudo systemctl reload sshd           # existing sessions stay open

Step 5: Prove it works from a SECOND terminal

$ ssh root@server1
root@server1: Permission denied (publickey,gssapi-keyex,gssapi-with-mic).    # root blocked
$ ssh -o PubkeyAuthentication=no admin1@server1
admin1@server1: Permission denied (publickey,gssapi-keyex,gssapi-with-mic).  # "password" is gone from the list
$ ssh admin1@server1                                                          # key still works

📍 Step 6: Firewall (only trusted IPs)

$ sudo firewall-cmd --permanent --remove-service=ssh
$ sudo firewall-cmd --permanent --add-rich-rule='rule family="ipv4" source address="192.168.1.0/24" service name="ssh" accept'
$ sudo firewall-cmd --reload
$ sudo firewall-cmd --list-all | grep -E 'services|rich'
Use a network range (/24) or a single admin IP. If you are not sure of your IP, skip this step.
If you change the port (Port 2222), you must also do both of these or sshd will not start or you cannot connect:
$ sudo semanage port -a -t ssh_port_t -p tcp 2222        # tell SELinux
$ sudo firewall-cmd --permanent --add-port=2222/tcp ; sudo firewall-cmd --reload
Changing the port only hides you from automatic scans. It is not real security. Keys-only is.

Step 7: Watch and ban

$ sudo journalctl -u sshd -f                  # live log. Also /var/log/secure
$ sudo grep "Failed password" /var/log/secure | tail -3
$ sudo lastb -n 5                              # failed logins
$ sudo dnf install -y epel-release fail2ban    # bans IPs after repeated failures
$ sudo systemctl enable --now fail2ban

📍 Where to Add What (fail2ban)

Create /etc/fail2ban/jail.local:
[sshd]
enabled  = true
maxretry = 3
bantime  = 1h
